# Security policy

## Reporting a vulnerability

**Do not open a public issue for a security problem.**

Use GitHub's private vulnerability reporting on this repository:
**Security → Report a vulnerability**. It goes only to the maintainers.

Please include what you found, how to reproduce it, and what an attacker could
do with it. A proof of concept helps enormously.

| Stage                  | Target                       |
| ---------------------- | ---------------------------- |
| Acknowledgement        | within 48 hours              |
| Initial assessment     | within 7 days                |
| Coordinated disclosure | within 90 days of the report |

There is no bug bounty. Reporters are credited in the release notes unless they
ask not to be.

## Safe harbour

We will not pursue or support legal action against anyone who reports a
vulnerability in good faith, stays within the scope below, avoids privacy
violations and service degradation, and gives us reasonable time to fix it
before disclosing.

## In scope

- This repository's application code, including the admin.
- The default configuration a user gets from the deploy instructions.
- Authentication, the first-run claim flow, and session handling.
- Anything that leaks a secret into the client bundle.

## Out of scope

- Third-party services (Supabase, Vercel, Resend and so on) — report those to
  the service.
- Misconfiguration by an operator who deviated from the documented setup.
- Missing security headers on a self-hosted deployment that did not apply the
  provided configuration.
- Free-tier exhaustion or denial of service by volume.
- Reports generated by a scanner with no demonstrated impact.

## Known limitations of the current release

This project is **pre-1.0 and not yet safe to deploy publicly.** These are known
and are being fixed, so they are not useful vulnerability reports:

- The admin gate is a `VITE_`-prefixed environment variable, which is compiled
  into the JavaScript bundle and readable by anyone who opens the site. **It is
  not authentication.**
- The login session is an unsigned object in `localStorage` and can be forged.
- There is no server, so content lives in the editor's own browser and the
  contact form does not deliver anything to the site owner.
- Uploaded files are not validated for type, size or content.

Real authentication, server-side sessions and upload validation arrive with the
Next.js migration. Until then, run the admin locally only.

## Supported versions

| Version | Supported           |
| ------- | ------------------- |
| 0.x     | Latest release only |

Until 1.0, fixes land on the latest release. There are no backports.
